# 基于 Agent 的高校校园智能事务处理平台 —— 需求分析文档

**版本：** 1.0  
**日期：** 2026年3月  

---

## 一、需求背景与范围

### 1.1 问题描述

当前高校校园信息系统存在以下典型问题：

1. **系统孤岛问题：** 宿舍报修、二手交易、失物招领、地图导航等系统相互独立，用户需要在不同入口频繁切换。
2. **交互门槛高：** 传统表单填写方式操作繁琐，信息不熟悉的新生尤为不便。
3. **缺乏智能推荐：** 二手交易依赖被动浏览，失物招领匹配全靠人工，效率低下。
4. **导航通用化：** 现有地图应用不理解校园语义（如"三号宿舍楼"、"西区食堂"），用户无法自然语言查询。
5. **无统一事务入口：** 用户没有一个地方可以"说一句话让系统帮我办"。

### 1.2 需求范围

本文档覆盖以下六个功能模块的需求分析：

1. 校园智能助手（Agent 核心）
2. 宿舍事务智能办理
3. 二手交易智能推荐
4. 失物招领智能匹配
5. 校园语义导航
6. 消息与提醒

---

## 二、用户角色定义

| 角色 | 描述 | 主要使用场景 |
|------|------|-------------|
| 普通学生 | 在校学生，系统主要用户群体 | 自然语言发起事务、浏览推荐结果、查询导航 |
| 宿舍管理员 | 负责宿舍楼的入住/退宿/报修管理 | 处理报修工单、管理宿舍信息 |
| 系统管理员 | 负责平台整体运营 | 用户管理、二手审核、公告发布 |
| Agent 系统 | 内部角色，代表用户自动调用各工具 | 工具调用、参数传递、结果汇聚 |

## 三、功能需求

### 3.1 校园智能助手模块

#### 3.1.1 自然语言输入

- **FR-A-01：** 系统应提供自然语言输入框，支持用户直接键入文本请求。
- **FR-A-02：** 系统应支持快捷指令卡片，用户点击后自动填充对应意图文本。
- **FR-A-03：** 系统应保留历史会话列表，用户可切换查看历史对话。

#### 3.1.2 意图识别

- **FR-A-04：** 系统应识别以下意图类型：
  - 查询类（查宿舍信息、查工单状态、查商品）
  - 办理类（报修、发布商品、发布失物）
  - 推荐类（推荐商品、推荐路线）
  - 导航类（地点查询、路线规划）
  - 失物匹配类（失物搜索、拾物发布）
  - 提醒类（设置提醒、查看通知）
- **FR-A-05：** 系统应将识别结果显示在右侧信息面板中，供用户确认。

#### 3.1.3 参数提取与追问

- **FR-A-06：** 系统应从用户输入中提取关键槽位（Slot），包括但不限于：地点、时间、物品类型、预算、数量、颜色等。
- **FR-A-07：** 当关键参数缺失时，系统应以自然语言追问用户，每次只追问一个参数。
- **FR-A-08：** 系统应在右侧面板实时展示已提取的参数与待补充的参数。

#### 3.1.4 任务拆解与工具调用

- **FR-A-09：** 系统应根据意图和参数，自动拆解任务，选择一个或多个工具顺序/并行调用。
- **FR-A-10：** 系统应在聊天区展示工具调用过程（如"正在搜索商品…"、"正在提交工单…"）。

#### 3.1.5 结果生成与展示

- **FR-A-11：** 系统应将工具调用结果汇总，生成自然语言回复和结构化卡片。
- **FR-A-12：** 结果卡片应包含跳转按钮，可直接进入对应业务页面。
#### 3.1.6 对话界面交互规范

- **FR-A-13：** 用户消息应展示在聊天区**右侧**，附带用户头像（右侧）；Agent 回复展示在**左侧**，附带机器人头像（左侧）。不得将用户消息展示在左侧。
- **FR-A-14：** 去除输入框上方的静态功能卡片。
- **FR-A-15：** 每轮 Agent 回复完成后（即未进行追问、任务已完成或阶段性回应），系统应动态生成 3～4 个「推荐追问」选项，以可点击气泡（Chip）的形式显示在回复内容之下。
- **FR-A-16：** 推荐追问内容必须与当前意图和结果相关，不得与上一轮内容重复。示例：
  - 导航完成后：「查看路线详情」「换骑行方案」「附近还有哪些…」
  - 失物完成后：「立即发布寻物信息」「查看相似招领」「补充丢失时间」
  - 报修完成后：「查看工单状态」「报修其他设备」「联系宿舍管理员」
- **FR-A-17：** Agent 回复区应分四个区域展示，不得只有纯文字：
  1. **自然语言解释**：对任务结果的口语化说明
  2. **结构化结果卡片**：工单卡片 / 商品卡片 / 路线卡片 / 失物匹配卡片﹣
  3. **推荐追问区**：3～4 个可点击的追问 Chip（任务完成后才显示）
  4. **跳转操作按鈕**：如「查看详情」「前往详情页」等

### 3.2 宿舍事务智能办理模块

#### 3.2.1 自然语言报修

- **FR-B-01：** 用户可通过自然语言描述故障，系统自动识别故障类型（空调、灯、网络、门锁、水管等）并填写工单。
- **FR-B-02：** 若缺失宿舍号，系统自动追问，优先使用用户主页绑定的宿舍信息。
- **FR-B-03：** 工单提交成功后，系统应返回工单号和当前状态。

#### 3.2.2 报修工单查询

- **FR-B-04：** 用户可通过自然语言或直接点击查询当前未完成工单列表及状态。
- **FR-B-05：** 支持按时间、状态过滤工单。

#### 3.2.3 宿舍信息查询

- **FR-B-06：** 用户可查询自己宿舍的基础信息（楼栋、房间号、入住人员）。
- **FR-B-07：** 宿舍管理员可查询宿舍楼整体入住情况。

#### 3.2.4 工单状态流转

- **FR-B-08：** 工单状态包含：待处理 → 处理中 → 已完成 / 已驳回。
- **FR-B-09：** 状态变更后，系统自动通过消息模块通知用户。

---

### 3.3 二手交易智能推荐模块

#### 3.3.1 自然语言商品搜索

- **FR-C-01：** 用户可通过自然语言描述商品需求（如"50 元以内的二手台灯"），系统自动提取类型、价格范围、偏好条件并进行检索。
- **FR-C-02：** 系统支持语义搜索，允许同义词匹配（如"电扇"匹配"电风扇"）。

#### 3.3.2 智能推荐

- **FR-C-03：** 系统对检索结果按价格、发布时间、与用户距离等维度综合排序。
- **FR-C-04：** 每个推荐商品应附带推荐理由（如"价格低于预算 30%"、"距离你最近"、"近 3 天发布"）。

#### 3.3.3 商品发布与审核

- **FR-C-05：** 用户可发布二手商品，包含标题、分类、价格、描述、图片。
- **FR-C-06：** 商品发布后须经管理员审核方可上架。

#### 3.3.4 商品详情与沟通

- **FR-C-07：** 用户可查看商品详情，通过站内消息联系卖家。
- **FR-C-08：** 支持商品收藏功能。

### 3.4 失物招领智能匹配模块

#### 3.4.0 模块信息架构与子模块命名

失物招领模块分为 4 个层次分明的子模块：

| 子模块名称 | 实质是 | 对谁展示 | 数据来源 |
|------------|------|----------|----------|
| **寻物公告** | 失主发布的「我丢了」公开信息 | 所有人可肝 | `lost_item`（所有人） |
| **招领公告** | 拾主发布的「我拾到了」公开信息 | 所有人可肝 | `found_item`（所有人） |
| **我的失物** | 我个人发布的寻物贴子 | 仅当前用户 | `lost_item`（user_id = 当前用户） |
| **我的招领** | 我个人发布的招领贴子 | 仅当前用户 | `found_item`（user_id = 当前用户） |

**命名理由：**
- 「公告」后缀明确表达“公共信息池”，“寻物」/「招领」分别表达两种角色
- 「我的」前缀明确表达“个人管理中心”，风格统一、易懂
- 适合页面菜单、模块标题、数据库字段命名和答輩表述

#### 3.4.1 寻物公告（失主视角）

- **FR-D-01：** 用户可在「寻物公告」 Tab 中查看全校展示的「我丢了XX」公开贴子列表。
- **FR-D-02：** 用户可发布自己的寻物信息，包括：物品名称、颜色、丢失地点、丢失时间、详细描述、图片。
- **FR-D-03：** 支持关键词搜索和分类筛选（按状态：寻找中 / 已找回）。

#### 3.4.2 招领公告（拾主视角）

- **FR-D-04：** 用户可在「招领公告」 Tab 中查看全校展示的「我拾到了XX」公开贴子列表。
- **FR-D-05：** 用户可发布自己的拜领信息，包括：物品名称、颜色、拾取地点、拾取时间、详细描述、图片。
- **FR-D-06：** 支持关键词搜索和分类筛选。

#### 3.4.3 我的失物 / 我的招领（个人管理）

- **FR-D-07：** 用户可在「我的失物」查看自己发布的寻物贴子，支持删除和状态更改（寻找中 → 已找回）。
- **FR-D-08：** 用户可在「我的招领」查看自己发布的招领贴子，支持删除和状态更改（持有中 → 已归还）。

#### 3.4.4 Agent 调用失物招领模块

- **FR-D-09：** 用户可在智能助手中直接说「我丢了一个黑色水杯，可能在图书馆」，Agent 应自动识别为「寻物求助」意图并进入参数填充流程。
- **FR-D-10：** Agent 应自动提取如下字段：物品名称、颜色、地点、时间、描述。
- **FR-D-11：** 当关键字段（物品名称）缺失时，Agent 应逐个追问补充。
- **FR-D-12：** 信息提交完毕后，Agent 应自动在招领公告中搜索相似记录并展示匹配候选列表。
- **FR-D-13：** 匹配结果卡片应包含「前往寻物公告」和「前往招领公告」跳转按鈕，实现 Agent 对话与业务页面的联动。
- **FR-D-14：** 相似度超过阈値时，系统应向失主和拾主双方主动发送消息提醒。
- **FR-D-15：** 用户可在 Agent 对话中查询自己发布的失物或招领信息状态。

#### 3.4.5 联系与状态管理

- **FR-D-16：** 用户可在寻物公告或招领公告中点击卸型联系拾主/失主，内容细节通过站内消息进行。
- **FR-D-17：** 双方确认物品归还后，必须将寻物记录状态更改为“已找回”、拜领记录状态更改为“已归还”。

### 3.5 校园语义导航模块

#### 3.5.1 自然语言地点查询

- **FR-E-01：** 支持用户输入校园语义地点（如"西区食堂"、"三号宿舍楼"、"图书馆"），系统解析为坐标进行路线规划。
- **FR-E-02：** 支持模糊查询，如"最近的打印店"。

#### 3.5.2 路线规划

- **FR-E-03：** 支持步行路线规划，展示距离和预计时间。
- **FR-E-04：** 支持多目标点导航（如"先去食堂再去图书馆"）。

#### 3.5.3 校园 POI 管理

- **FR-E-05：** 系统内置校园 POI 数据，管理员可增删改。
- **FR-E-06：** 用户可收藏常用地点，快速发起导航。
#### 3.5.4 Agent 导航深链与页面联动（重点新增）

- **FR-E-07：** Agent 回复的路线结果卡片应包含「查看地图」按鈕，点击后应跳转到导航页，并**自动携带**起点、终点、出行方式等参数。
- **FR-E-08：** 导航页（`/navigation`）应支持通过 URL 参数接收路线信息，参数格式：
  ```
  /navigation?from=agent&origin=三号宿舍楼&dest=图书馆&mode=walking
  ```
- **FR-E-09：** 当 URL 中包含 `from=agent` 时，页面进入后应**自动触发**路线规划，无需用户手动点击。应直接进入「路线就绪」状态展示结果。
- **FR-E-10：** 导航页应具备明确的页面状态模型：
  - **空闲状态**：未有路线，展示搜索表单和常用地点
  - **加载中状态**：路线规划中，展示祛轉动画和进度提示
  - **路线就绪状态**：展示路线摘要卡片、步骤列表、地图高亮路线、操作按鈕
- **FR-E-11：** 路线就绪状态下，地图应自动高亮路线（科大蓝路线），起点绿色标忦，终点红色标忦，自动调节视图跳转至全路线范围。
- **FR-E-12：** 导航页应在左侧面板显示路线摘要（距离、预计时间）和逐步路段说明（`el-steps`），方便用户按步行进。
- **FR-E-13：** 导航页应提供「重新搜索」按鈕，点击后回到空闲状态，方便用户重新输入起终点。

### 3.6 消息与提醒模块

#### 3.6.1 站内消息

- **FR-F-01：** 支持用户之间发送站内消息（用于二手沟通、失物联系）。
- **FR-F-02：** 支持消息未读数角标展示。

#### 3.6.2 系统通知

- **FR-F-03：** Agent 办理结果（如报修提交成功）应通过系统通知推送给用户。
- **FR-F-04：** 工单状态变更时自动通知用户。
- **FR-F-05：** 失物匹配成功时自动通知双方用户。
- **FR-F-06：** 商品审核通过/驳回后自动通知发布者。

## 四、非功能需求

### 4.1 性能需求

| 指标 | 要求 |
|------|------|
| 页面首屏加载时间 | ≤ 3 秒 |
| 普通 API 响应时间 | ≤ 1 秒 |
| Agent 意图识别响应时间 | ≤ 5 秒（含大模型调用） |
| 并发用户支持 | ≥ 100（演示环境） |

### 4.2 安全性需求

- **NFR-S-01：** 所有 API 须经过 JWT Token 鉴权，Agent 调用工具时沿用当前用户身份。
- **NFR-S-02：** 大模型调用的 API Key 不得在前端暴露，须通过后端代理调用。
- **NFR-S-03：** 用户输入须进行 XSS 防护和 SQL 注入防护。
- **NFR-S-04：** 文件上传须限制类型（图片类）和大小（≤ 10MB）。
- **NFR-S-05：** 敏感操作（如工单提交、商品发布）须记录操作日志。

### 4.3 可用性需求

- **NFR-U-01：** 系统主要功能应在无障碍模式下可访问。
- **NFR-U-02：** 移动端浏览器应能正常访问前端（响应式布局）。
- **NFR-U-03：** Agent 调用失败时应给出明确的降级提示，不允许静默失败。

### 4.4 可维护性需求

- **NFR-M-01：** 工具注册表应支持动态扩展，新增工具不需修改 Agent 核心逻辑。
- **NFR-M-02：** 大模型接口应通过统一抽象层调用，便于切换模型提供商。
- **NFR-M-03：** 关键操作日志须可查询，保留至少 30 天。

## 五、约束条件

| 类型 | 约束说明 |
|------|----------|
| 技术约束 | 后端使用 Spring Boot，前端使用 Vue 3，不可整体推翻改写 |
| 数据约束 | 校园 POI 数据来自高德地图 API 或本地维护 |
| 模型约束 | 大模型调用须使用 OpenAI 兼容接口（DeepSeek / 通义千问等） |
| 部署约束 | 演示环境为本地或云服务器，不依赖特定企业内网 |
| 时间约束 | 毕业设计答辩前须完成核心功能演示 |

## 六、需求优先级

### P0（必须实现）
- Agent 意图识别与参数提取
- 宿舍报修自然语言办理
- 二手商品自然语言搜索与推荐
- 失物招领语义匹配（含 4 子模块命名与查看）
- 智能助手首页入口与聊天页面
- 聊天界面用户消息展示在右侧（FR-A-13）
- 办理结果消息通知

### P1（应该实现）
- 工单状态追踪与通知
- 多轮对话参数追问
- 推荐理由展示
- Agent 导航深链（FR-E-07~13）：导航页自动加载 Agent 路线结果
- 失物匹配提醒推送
- 动态追问推荐（FR-A-15~16）

### P2（有余力实现）
- 校园语义导航多目标点
- Redis 缓存热点数据
- Agent 调用日志可视化

## 七、用户故事示例

### US-001：宿舍报修

> 作为一名学生，我想对着输入框说"我宿舍灯坏了"，系统帮我自动报修，这样我不需要手动填写复杂的报修表单。

**验收标准：**
1. 系统识别意图为"宿舍报修"
2. 自动提取故障类型"灯损坏"
3. 若未绑定宿舍，追问"请问你的宿舍号是？"
4. 用户补充后，提交工单
5. 显示"工单提交成功，工单号 XXXX，状态：待处理"

---

### US-002：二手商品推荐

> 作为一名新生，我想找一个 50 元以内的二手台灯，但不知道去哪找，我希望通过描述需求，系统自动帮我推荐。

**验收标准：**
1. 系统识别意图为"商品推荐"
2. 提取商品类型"台灯"、价格上限"50元"
3. 调用二手搜索工具，过滤价格
4. 返回推荐列表，每项附带推荐理由
5. 点击商品可跳转商品详情页

---

### US-003：失物招领匹配

> 作为一名失主，我丢了一个黑色保温杯，可能在图书馆，我希望系统能自动帮我查找是否有人捡到类似物品。

**验收标准：**
1. 用户输入描述，系统提取：物品类型"保温杯"、颜色"黑色"、地点"图书馆"
2. 调用失物匹配工具，返回相似度排序的拾物记录
3. 用户可点击记录，通过消息联系对方
4. 若相似度超过阈值，系统主动通知拾主

### US-004：校园导航（含 Agent 深链跳转）

> 作为一名学生，我想从三号宿舍楼步行去图书馆，我希望用自然语言描述出发地和目的地，系统帮我规划路线。点击卡片后希望进入导航页**直接看到路线**，而不是需要重新输入起终点。

**验收标准：**
1. 系统识别意图为"导航"
2. 解析"三号宿舍楼"和"图书馆"为校园 POI 坐标
3. 调用高德地图 API 规划步行路线
4. 返回路线摘要卡片（距离、时间）并附带"查看地图"按钮
5. 点击"查看地图"，页面跳转到 `/navigation?from=agent&origin=三号宿舍楼&dest=图书馆&mode=walking`
6. 导航页自动触发路线规划，地图高亮路线，左侧面板显示路线摘要和步骤列表

### US-005：失物招领 Agent 发布与跳转

> 作为一名学生，我丢了一个黑色水杯，可能在操场附近，我希望通过对话直接发布寻物信息，并能在专属页面管理我的失物帖。

**验收标准：**
1. 系统识别意图为 `LOSTFOUND_LOST`
2. 自动提取：物品名称"水杯"、颜色"黑色"、地点"操场"
3. 若时间未提供，追问"大概是什么时候丢的？"
4. 信息完整后，创建失物记录（写入 `lost_item` 表，user_id 绑定当前用户）
5. 在招领公告中搜索相似物品，展示匹配候选列表
6. 回复包含"前往寻物公告"跳转按钮，点击进入 `/lostfound?tab=notices`
7. 用户可在"我的失物"Tab 下查看和管理自己发布的寻物帖

### US-006：动态追问推荐体验

> 作为一名用户，我提交了报修请求后，希望系统能主动提示"我还能做什么"，而不是等我自己想下一步操作。

**验收标准：**
1. Agent 完成报修任务后，回复下方显示 3 个推荐追问 Chip
2. Chip 内容与当前场景相关，如"查看工单状态"、"报修其他设备"、"联系宿管"
3. 点击 Chip，自动发送对应内容，Agent 继续响应
4. 下一轮回复完成后，Chip 内容更新为新场景推荐
5. 静态区域不出现固定的"预设问题卡片"

## 八、系统边界说明

**在系统范围内：**
- 自然语言事务办理（报修、查询、推荐、匹配）
- 校园业务模块的 Agent 工具封装
- 站内用户消息通知
- 校园 POI 导航

**不在系统范围内：**
- 财务结算与支付功能
- 与学校教务系统的对接
- 实时定位追踪
- 对话情感分析（非核心功能）
